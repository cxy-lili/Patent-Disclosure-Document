# 专利附图与框架图

按技术对象选择方法流程图、结构图、电路／控制图或工艺图。以下图模型、门控和训练边界的例子仅在对应方案中使用，不要求其他领域添加这些模块。

## 附图规划

按需要证明的技术关系选图：总体方法、技术架构、核心创新机制、训练边界、系统结构、异常及版本处理。图的数量不是目标。用户问哪些图必须保留时，按技术说明需要分级，不把建议说成法律强制要求。

每幅图给出：图号与图名、表达目的、节点／模块、关键连线、公式、分支条件。单独机制图与总体框架图各有作用；不把所有细节塞进框架图。

## 框架图审查顺序

1. **正向计算**：输入来自哪里，各模块是否真正连通；图模型是否具备节点特征和图结构输入；时序模块是否有历史序列。总体图可用注释简化输入细节，不必逐项新增框。
2. **关键运算**：公式与箭头是否一致；是否存在绕过门控或核验的捷径；核验、映射、注入发生在预测之前还是之后。
3. **训练边界**：哪些参数固定、哪些可训练；损失是否能回传到应训练的参数；冻结模型不更新参数但可传递输入梯度。验证数据不参与训练梯度。
4. **推理边界**：线上仅前向计算，使用兼容的模型、提示及任务头版本；零提示与缺少兼容任务头不能混为同一种状态。
5. **规则与反馈**：规则更新能否定位依赖版本、暂停旧版本、触发重新核验及重新发布；真实结果经观察期和完整性检查后形成训练标签。
6. **表达质量**：空白框、多余占位文字、箭头方向、图例线型、下标、过小字体和交叉线。先解决逻辑问题，再优化布局。

区分“计算流程箭头”和“发布、控制或数据回流箭头”，避免所有关系都画成相同的计算链。不要将训练／验证通过直接连到业务预测结果；应连接发布或在线调用环节。

## 评审意见格式

先说明总体可用程度，然后只列当前图片中仍存在的问题。每项包括：

- 位置：引用现有框名或两框之间的连线。
- 问题：该表达会造成什么具体误解。
- 修改：删哪条线、从哪里连接到哪里、箭头朝向与标签。

对分辨率不足或被遮挡的部分，先局部检查；仍看不清就标为未确认，不猜测缺失。不能因为对话中曾指出某问题，就认定新版仍有该问题。

正文与图互相核对时，逐处检查“如图X所示”以及无“如”字的图引用。条件不同的分支不得共用模糊标签：例如当前请求零门控，不自动等于目标提示版本缺失，也不自动表示必须切换任务头。图中采用基础方式的注入位置或更新示意时，与对应正文限定一致；不要据此否定已明确允许的逐层提示替代方式。

## 避免交叉的连接符

跨区域数据回流可以使用两个同名圆形连接符，例如：

```text
底部：成熟标签 → Ⓐ
中部：Ⓐ → 少量成熟标签及标签掩码
```

两个 Ⓐ 之间不再画长线。图例写“同字母圆形连接符表示同一条跨区域数据通路”。两端短线采用样本反馈线型。每一组跨区域通路使用独立字母，防止多条不同数据流被误连。

## 绘图 prompt

用可复制的完整 prompt 描述以下内容，不只给审美关键词：

- 用途和风格：中文专利技术框架、白底黑线、矩形模块、可读文字；是否允许颜色以用户参考为准。
- 布局与层级：阶段、支路、共享输入、主流程和反馈区。
- 每个框的准确文字、核心公式及上下标。
- 全部关键连线：源、目标、方向、线型和标签。
- 明确避免的技术误画：门控旁路、梯度进入固定证据核验、失效版本继续启用等。
- 输出要求：没有“Text”等占位字；保持字号与留白；用户要源文件时不能用栅格图替代。

## draw.io 可编辑交付

为每个模块、文字、运算符、边界和连接线建立原生 mxGraph 图元，使用唯一 ID、有效的边端点和必要的折线路径。公式保留可编辑文字或工具支持的数学表达。不可把整张图片嵌入一个图元后称为可编辑重绘。

核对 XML 解析、图元及边引用、预览布局、文字溢出、线头和图例。可同时交付 SVG／PNG 预览，但 .drawio 是可编辑交付本体。用户要求忠实重绘而原图存在技术问题时，说明问题；不要默默改变技术关系。

若用户要求在网站打开绘制，使用可用浏览器工具；网站操作失败时不能声称已经完成。用户随后要求本地源文件，则完成本地交付即可，不必持续重试浏览器。
